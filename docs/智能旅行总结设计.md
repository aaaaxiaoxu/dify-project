# 智能旅行总结设计

## 结论

这个功能不要做成“只有 Dify 工作流”的方案。

更合适的做法是：

1. 前端个人中心提供“生成旅行报告”入口，用户主动选择时间范围。
2. 后端根据当前登录用户和时间范围，从数据库里筛出日记与 AI 分析结果。
3. 后端先做一次结构化聚合，再把聚合后的 JSON 交给一个新的 Dify 工作流生成报告。
4. 后端把报告结果返回前端，后续如果需要可以落库缓存。

原因很直接：

- 时间范围筛选、权限校验、用户隔离，应该在后端做，不应该交给 Dify。
- 你现在的 Dify 接入是“单篇日记分析”，输入是文本/图片/视频，不适合直接扩成“跨多篇日记生成报告”。
- 如果让 Dify 直接去查数据库或调内部接口，复杂度会比“后端聚合 + Dify 写作”高很多。

## 现有项目基础

当前项目已经有这些基础，可以直接复用：

- 单篇 AI 分析工作流文件：`TravelDiaryAI智能分析.yml`
- Dify 调用封装：`backend2/utils/dify_client.py`
- AI 分析结果存储表：`ai_analysis`
- 日记表：`diaries`
- 个人中心页面：`diary2/pages/profile/profile.vue`

当前 DifyClient 的特点：

- 默认走一个工作流 API Key。
- 默认解析 `analysis_result` 这个输出字段。
- 逻辑是给单篇日记做分析，不是给一段时间内的多篇内容做总结。

所以旅行报告建议单独做一个新的工作流，不要塞进现在这个分析工作流里。

## 推荐方案

### 一句话架构

前端选范围 -> 后端查日记并聚合 -> 新 Dify 工作流生成报告 -> 前端展示/分享

### MVP 范围

先做“用户主动生成 + 自定义时间范围”，不做自动定时、不做复杂分享。

MVP 建议包含：

- 个人中心新增“智能旅行总结”入口
- 支持预设范围：近 7 天、近 30 天、全部
- 支持自定义开始/结束日期
- 点击后生成一份报告
- 报告内容支持页面展示

MVP 不建议一开始就做：

- 自动定时生成
- PDF 导出
- 富图文排版
- 多版本报告历史
- 多模型切换

## 后端应该做什么

### 1. 新增报告聚合接口

建议新增接口：

- `POST /api/report/generate`

请求示例：

```json
{
  "start_date": "2026-01-01",
  "end_date": "2026-03-31"
}
```

后端职责：

- 校验登录用户
- 校验日期范围
- 查询该用户在范围内的所有非草稿日记
- 关联 `ai_analysis`
- 把原始日记整理成适合大模型消费的结构化摘要
- 调 Dify 生成报告
- 返回报告 JSON

### 2. 不要把所有原文直接扔给 Dify

这里是关键。

如果用户有很多篇日记，直接把完整内容拼进去，会有两个问题：

- token 成本高
- 输出容易发散

正确做法是后端先聚合，生成一个压缩版上下文。

建议聚合出的结构示例：

```json
{
  "period": {
    "start_date": "2026-01-01",
    "end_date": "2026-03-31"
  },
  "summary_stats": {
    "diary_count": 12,
    "city_count": 5,
    "avg_emotion_score": 0.4
  },
  "locations": [
    {"name": "杭州西湖", "count": 3},
    {"name": "苏州园林", "count": 2}
  ],
  "emotion_distribution": [
    {"label": "积极", "count": 8},
    {"label": "中性", "count": 3},
    {"label": "消极", "count": 1}
  ],
  "highlights": [
    {
      "date": "2026-03-02",
      "title": "西湖日落",
      "location": "杭州西湖",
      "emotion_score": 0.9,
      "emotion_label": "开心",
      "memory_point": "雷峰塔下看见湖面晚霞",
      "keywords": ["西湖", "日落", "游船"],
      "excerpt": "傍晚时分湖面泛起金色涟漪。"
    }
  ]
}
```

建议控制规则：

- `highlights` 只取 5 到 8 篇代表性日记
- 每篇 `excerpt` 截断到 80 到 120 字
- `keywords` 只保留前 3 到 5 个
- `memory_point` 有值优先保留
- 情绪分最低和最高的日记都尽量至少保留一篇

### 3. 生成报告时复用 AIAnalysis

你现在已经把这些数据存下来了：

- `emotion_score`
- `emotion_label`
- `keywords`
- `travel_advice`
- `memory_point`

这很好，说明报告生成不需要重新逐篇做 AI 分析。

报告功能应该优先复用已有分析结果，只在缺失时再做回退处理。

## Dify 工作流应该做什么

### 推荐：单独新建一个工作流

建议名称：

- `TravelDiaryAI智能旅行总结`

不要复用现有 `TravelDiaryAI智能分析`，因为两者职责不同：

- 当前工作流负责“单篇内容分析”
- 新工作流负责“多篇聚合后写报告”

### 工作流复杂度

这个新工作流其实不需要很复杂。

建议最简单的结构就是：

- Start
- LLM
- End

不需要：

- 图片分析节点
- 视频分析节点
- 工具调用
- 条件分支

因为这些都应该在“单篇分析”阶段完成，不应该在“总结阶段”再来一遍。

### Start 输入建议

建议 Dify Start 节点接收这些字段：

- `report_context_json`：后端聚合后的 JSON 字符串
- `start_date`
- `end_date`
- `report_style`

其中：

- `report_style` 可以先固定成 `warm`
- 后续如果你要支持“故事型 / 数据型 / 极简型”，再扩这个字段

### Dify 输出建议

不要只输出一段长文本。

建议输出结构化 JSON，后端和前端会更好接。

建议输出：

```json
{
  "report_title": "2026 春日江南旅行总结",
  "report_subtitle": "从西湖到园林，这段旅程整体情绪积极而舒展",
  "summary": "本次旅程覆盖 5 个地点，共记录 12 篇日记，整体情绪评分为 0.4。",
  "highlights": [
    "在杭州西湖的傍晚时刻留下了最强烈的积极体验。",
    "苏州园林相关记录最集中，说明你对古典园林有明显偏好。"
  ],
  "emotion_review": "整体情绪偏积极，中段略有波动，后期重新回到高点。",
  "travel_preferences": [
    "偏好自然与人文结合的目的地",
    "对傍晚景色和慢节奏步行体验敏感",
    "更容易在有历史感的场景中形成记忆点"
  ],
  "next_trip_suggestions": [
    "可以尝试乌镇或绍兴这类水乡目的地",
    "适合增加夜景和清晨散步类行程"
  ],
  "memory_quote": "最值得记住的不是赶路，而是在风景里真正停下来。"
}
```

### Dify System Prompt 建议

可以直接用这版作为第一稿：

```text
你是一个旅行总结助手。你的任务不是分析单篇日记，而是基于一段时间内多篇旅行日记的聚合数据，生成一份清晰、温暖、具体的旅行报告。

规则：
1. 输入是已经过后端聚合的旅行数据 JSON，请严格基于输入生成，不要虚构不存在的地点、事件或情绪变化。
2. 语言要自然、有总结感，但不要过度抒情。
3. 优先引用输入中的 memory_point、keywords、emotion_score、location、title 等结构化信息。
4. 如果输入里某部分缺失，不要编造，用更保守的总结表达。
5. 输出必须是 JSON，不要输出 Markdown，不要加解释。
6. highlights 输出 3-5 条短句；travel_preferences 和 next_trip_suggestions 分别输出 2-4 条。
7. summary、emotion_review、memory_quote 要可直接给用户展示。

输入：
时间范围：{{start_date}} 到 {{end_date}}
报告风格：{{report_style}}
聚合数据：
{{report_context_json}}

输出格式：
{
  "report_title": "",
  "report_subtitle": "",
  "summary": "",
  "highlights": [],
  "emotion_review": "",
  "travel_preferences": [],
  "next_trip_suggestions": [],
  "memory_quote": ""
}
```

## 为什么不建议让 Dify 直接查数据

表面上看，把“查日记 + 总结”都塞给 Dify 很省事，实际上不是。

问题包括：

- 需要额外暴露内部接口给 Dify 调用
- 还要处理用户鉴权
- 时间范围筛选要重复实现
- 一旦数据量变大，工作流会变得很难维护

你现在这个项目是标准前后端分层，报告数据源又都在本地数据库里，最稳妥的方式就是后端先准备好输入。

## 数据库存储建议

MVP 可以不落库，直接实时生成并返回。

如果后面要优化体验，再加一张表：

- `travel_reports`

建议字段：

- `id`
- `user_id`
- `start_date`
- `end_date`
- `report_title`
- `report_payload`
- `created_at`
- `updated_at`

作用：

- 同一时间范围重复打开时直接读缓存
- 支持报告历史
- 支持后续分享和导出

## 对你当前项目最适合的实施顺序

### 第一步

后端先实现聚合函数，不接 Dify，只返回 `report_context_json`。

目的：

- 先确认你抽出来的数据是不是好用
- 这一步做对了，后面接任何模型都容易

### 第二步

新建 Dify 工作流 `TravelDiaryAI智能旅行总结`，只吃聚合 JSON，输出报告 JSON。

### 第三步

后端新增 `generate_report` 调用，复用现在 `DifyClient` 的调用方式，但单独做一个报告解析方法，不要和 `analysis_result` 混在一起。

### 第四步

个人中心加入口和展示页。
